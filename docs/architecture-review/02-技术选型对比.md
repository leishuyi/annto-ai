# annto AI 套件 — 技术选型对比与决策记录

## 一、总体技术栈选型

| 维度 | 选定方案 | 备选 A | 备选 B | 决策理由 |
|------|---------|--------|--------|---------|
| 后端框架 | **FastAPI** | Flask | Django Ninja | FastAPI 原生 async、自动 OpenAPI、Pydantic v2 集成，性能最优 |
| ORM | **SQLAlchemy 2.0** | Tortoise ORM | SQLModel | SQLAlchemy 生态最成熟、迁移工具链完善、异步支持稳定 |
| 数据库 | **PostgreSQL** | MySQL 8.0 | SQLite | PG 的 JSONB/向量插件/并行查询适合 AI 场景，SQLite 仅用于开发 |
| 缓存/事件 | **Redis** | RabbitMQ | NATS | Redis 兼顾缓存 + Stream 事件总线，减少运维组件数 |
| 对象存储 | **MinIO** | S3 | 阿里云OSS | MinIO 完全兼容 S3 API，私有化部署，适合内网场景 |
| LLM 推理 | **DeepSeek-R1** | Qwen2.5 | GPT-4o | DeepSeek 性价比最高，安得已接入，中文效果优秀 |
| 多模态 | **Qwen-VL** | GPT-4V | GLM-4V | Qwen-VL 可私有部署，单据识别场景足够，成本可控 |
| OCR | **PaddleOCR** | Tesseract | 阿里云OCR | PaddleOCR 中文识别率最高、开源、支持自定义训练 |
| Agent 框架 | **自研 A2A** | LangGraph | CrewAI | 自研框架与安得 69 套系统对接更灵活，避免框架锁定 |
| 前端 | **React + Ant Design** | Vue3 + Element | 原生 H5 | React 生态最成熟、TypeScript 支持好、AntD 组件丰富 |
| 容器化 | **Docker Compose** | Kubernetes | Nomad | Docker Compose 在 MVP 阶段足够，K8s 后续演进 |

## 二、Agent 通信协议选型

| 方案 | 延迟 | 吞吐 | 持久化 | 复杂度 | 结论 |
|------|------|------|--------|--------|------|
| 进程内 dataclass | < 1μs | 极高 | ❌ | 低 | ✅ MVP 阶段采用 |
| Redis Streams | < 1ms | 高 | ✅ | 中 | 生产环境升级目标 |
| RabbitMQ | < 5ms | 高 | ✅ | 中 | 可替代方案 |
| gRPC | < 1ms | 极高 | ❌ | 高 | 跨语言/跨进程时使用 |
| Celery Task Queue | < 10ms | 高 | ✅ | 中 | 异步任务编排用 |

**决策**: MVP 用进程内 dataclass，生产用 Redis Streams + Celery。

## 三、认证方案选型

| 方案 | 实现成本 | 安全性 | 可扩展性 | 结论 |
|------|---------|--------|---------|------|
| API Key (Header) | 低 | 中 | 低 | ✅ MVP 阶段 |
| JWT Bearer | 中 | 高 | 高 | ✅ 生产目标 |
| OAuth2 + OIDC | 高 | 最高 | 高 | 企业 SSO 集成时 |
| Session + Cookie | 中 | 高 | 中 | 不适用 API 场景 |

**决策**: MVP 用 API Key，生产迁移到 JWT + RBAC。

## 四、P2 OCR 引擎选型对比

| 指标 | PaddleOCR | Tesseract 5 | 阿里云OCR |
|------|-----------|-------------|-----------|
| 中文识别率 | **98.5%** | 85% | 99% |
| 发票专用模型 | ✅ | ❌ | ✅ |
| 私有化部署 | ✅ | ✅ | ❌ |
| 自定义训练 | ✅ | ✅ | ❌ |
| 开源 | ✅ Apache 2.0 | ✅ | ❌ |
