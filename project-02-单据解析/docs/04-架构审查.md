# P2 多模态物流单据解析引擎 — 架构审查

> 审查日期：2026-07-24 | 审查人：资深架构师

## 业务对齐分析

### 安得实际业务需求

安得智联的自动录单是其智能客服体系的核心能力，定位为"AI 自动识别运单信息，减少人工录入"：

| 业务需求 | 说明 | 优先级 |
|---------|------|--------|
| 多模态单据识别 | 拍照（手机上传）/扫描/PDF 等多种输入 | P0 |
| 21 行业覆盖 | 家电、快消、汽车等 21 个垂直行业单据格式 | P0 |
| 高准确率自动录单 | 直接关联客服体验，错误导致客诉 | P0 |
| 与客服流程集成 | 录单是客服流程的一环，非独立功能 | P0 |
| 增量学习 | 新单据类型持续接入，模型持续优化 | P1 |

### 🚨 致命问题

| # | 问题 | 严重性 | 说明 |
|---|------|--------|------|
| F1 | **与 P1 客服流程完全割裂** | 🔴 致命 | 业务中自动录单是客服流程的一环，但 P2 作为独立项目运行，P1 无法调用 P2 能力，无 API 契约、无集成方案 |
| F2 | **不支持多模态输入** | 🟠 严重 | 安得现场场景包含手机拍照（模糊/倾斜/光照不均）、扫描仪（高分辨率）、PDF（电子版），需不同预处理管线，当前假设单一输入 |
| F3 | **无 21 行业分类体系** | 🟠 严重 | 安得覆盖 21 个垂直行业，各行业单据格式差异巨大（家电运单 vs 快消配送单），当前 5 类关键词分类远不满足 |
| F4 | **无增量学习机制** | 🟠 严重 | 新客户/新单据类型持续接入，无反馈闭环则准确率无法持续提升 |

## 架构模式

管线架构（Pipeline Architecture）

```
输入(拍照/扫描/PDF)
  → 多模态路由(按源类型分流)              ← ❌ 新增（纠偏 F2）
    → 图像预处理(倾斜校正/二值化/去噪)      ← ❌ 当前缺失
      → 文档分类(基于21行业 + LLM 双路)    ← ⚠️ 修复中
        → OCR 文字提取(PaddleOCR)         ← ⚠️ 当前 mock
          → 字段提取(按行业类型模板)        ← ⚠️ 硬编码
            → 逻辑校验(跨字段一致性)        ← ❌ 缺失
              → 置信度校准(边际分析)        ← ❌ 缺失
                → 输出结构化 JSON
```

### 多模态输入路由（新增）

```
输入 → Source-Type 检测
  ├── "mobile_photo" → 强去噪 + 倾斜校正 + 增强对比度
  ├── "scanner"      → 轻量预处理 + 保持原分辨率
  ├── "pdf"          → PDF 解析 → 页面提取 → 按页处理
  └── "unknown"      → 通用预处理 + LLM 辅助识别
```

## 技术选型（更新）

| 维度 | 原方案 | 修正方案 | 理由 |

| 容器化 | Docker Compose | **Kubernetes** | 与安得 K8s 集群统一 |

| 模板管理 | 硬编码 | **行业模板仓库 + GitOps 管理** | 21 行业模板需版本管理 |

### OCR 引擎选型对比

| 指标 | PaddleOCR | Tesseract 5 | 阿里云OCR |
|------|-----------|-------------|-----------|
| 中文识别率 | **98.5%** | 85% | 99% |
| 发票专用模型 | ✅ | ❌ | ✅ |
| 私有化部署 | ✅ | ✅ | ❌ |
| 自定义训练 | ✅ | ✅ | ❌ |
| 开源 | ✅ Apache 2.0 | ✅ | ❌ |
| 成本 | 免费 | 免费 | 按量计费 |

**决策**：PaddleOCR（可私有部署 + 可自定义训练物流专用模型 + 可与安得现有基础设施集成）。

## 场景缺口与重构

### 1. 缺少图像预处理

真实场景需要：上传 → **倾斜校正** → **二值化** → **去噪** → OCR → 分类 → 提取

### 2. 缺少 LLM 分类回退

当前分类器：关键词匹配（5 类，正确率约 70%）

目标：21 行业双路分类器
```
关键词分类 → 置信度 > 0.85 → 直接输出
           → 置信度 0.5-0.85 → LLM 二次确认
           → 置信度 < 0.5 → 返回 "不确定" + top-3 候选
```

### 3. 缺少置信度校准

引入边际分析：
```
final_confidence = (best_conf - second_best_conf) / best_conf
if final_confidence > 0.3 → 自动处理
elif final_confidence > 0.15 → 人工抽检
else → 强制人工
```

### 4. 缺少持久化

需增加 PostgreSQL 表 + 查询历史 + 批量导入。

### 5. 新增：P1↔P2 集成方案（纠偏 F1）

```python
# P2 作为独立的微服务，通过 API Gateway 被 P1 编排
# P1 Agent B（单据录入）调用 P2 API：

POST /api/v2/documents/parse
Request:  { image: bytes, source_type: "mobile_photo", industry: "家电" }
Response: { doc_id, fields: {...}, confidence: 0.92, status: "auto_approved" }

# 异步回调：P2 解析完成 → 事件总线 → P1 继续流转
```
