# 面试高频问题 — 一线人员智能助手

## Q1：7 个功能模块全是 mock，这能叫智能助手吗？

**坦诚回答**：当前是 mock，但每个模块的接口契约、数据结构、前端交互都按生产标准设计。

| 模块 | 当前 | 生产方案 | 替换工时 |
|------|------|---------|---------|
| 导航 | 硬编码 1850km | 高德 Maps API 货车路线 | 2 周 |
| 签收 | 永远返回成功 | PaddleOCR + 图像分类 | 2 周 |
| 话术 | 5 个关键词 | DeepSeek 情绪识别 | 2 周 |
| 上报 | 否定词检测 | ASR + NER 实体提取 | 2 周 |
| RPA | MD5 种子随机 | 对接 SAP/金蝶/用友 | 4 周 |
| 排班 | 3 个硬编码司机 | OR-Tools 约束求解 | 3 周 |
| 预警 | 3 条静态数据 | 实时规则引擎 | 2 周 |

**Mock 的意义**：接口定好后前后端可并行开发，不依赖真实 API 接入进度。

## Q2：为什么没有离线能力？配送途中网络不好怎么办？

**风险**：73,000~77,000 名司机长期处于弱网状态，纯在线设计不可用。

**这是架构审查标记的致命问题**。修复方案（Phase 1）：

```python
class OfflineEngine:
    SYNC_STRATEGIES = {
        "routes": "preload_all",     # 路线预加载
        "signoff": "offline_queue",  # 签收离线队列
        "alerts": "push_based",      # 预警推送
    }
```

**技术选型**：前端升级 PWA（Service Worker + IndexedDB）。

## Q3：送装一体（2,720 万单/年）为什么没做？

**根因**：MVP 聚焦"司机配送"场景，忽略了"安装服务"。

**送装一体核心流程**：
```
预约 → 师傅指派 → 上门服务 → 完工确认 → 客户评价
```

**排期**：Phase 1 核心补全（6 周）。

## Q4：预警系统怎么保证不误报？

**防误报机制**：
1. **确认窗口**：预警触发后等待 N 分钟，状态恢复则自动取消
2. **分级推送**：critical → 即时 | warning → 汇总 | info → 日报
3. **根因分析**：预警附带根因分析结果

## Q5：RPA 的 MD5 种子随机数是怎么回事？

**解释**：这是**确定性 Mock**，同一个月对账返回相同结果，方便前端调试。

```python
seed = int(hashlib.md5(period.encode()).hexdigest()[:8], 16)
total = 150 + (seed % 20)  # 同一月份始终相同
```

**生产目标**：对接 SAP/金蝶/用友 API，差异分析调用 DeepSeek。

## Q6：话术助手的 Prompt Injection 防护有效吗？

**三层防护**：
1. **系统提示词指令**：明确禁止角色扮演和泄露
2. **输入包装**：用户输入放在"客户说"前缀中
3. **输出限制**：`ScriptResponse` 结构化约束（只允许两个字段）

**当前局限**：无真实 LLM 情况下无法验证，接入 DeepSeek 后需专项测试。

## Q7：司机端和运营端合在一起会不会太复杂？

| 维度 | 司机端 | 运营端 |
|------|--------|--------|
| 使用场景 | 配送途中，移动端 | 办公室，桌面端 |
| 网络环境 | 不稳定 | 稳定 |

**后续优化**：拆分为独立部署单元，司机用 PWA 移动端，运营用 Web 桌面端。合在一起是为了 MVP 快速验证。
