## 架构模式

分层 + 事件驱动 + A2A Agent 协同。

| 层 | 职责 | 技术 |
|----|------|------|
| 接入层 | HTTP 路由、认证、限流、租户识别 | FastAPI + JWT + TenantMiddleware |
| 编排层 | Agent 链路调度、状态管理 | AgentOrchestrator + Celery |
| Agent 层 | 业务逻辑处理 | 6 个独立 Agent + 预警 Agent |
| 协议层 | Agent 间通信 | A2AMessage (dataclass) |
| 事件层 | 跨 Agent 通知 / 实时推送 | Redis Streams + WebSocket |
| 持久层 | 数据存储 | PostgreSQL + SQLAlchemy（Schema per Tenant）|
| 可观测层 | 日志/指标/追踪 | 集成博睿数据 Bonree ONE（安得已有） |

### Agent 链设计

```
串行段 A(订单查询) → B(单据录入)
                ↓
并行段 C(财务对账) ‖ D(调度校验)  ← feature_agent_parallel=true
                ↓
串行段 E(风控检测) → F(结论汇总)
                ↓
          人工授权 Gate
                ↓
新增: G(轨迹追踪) → H(预警推送)  ← 全链路可视 + 异常预警
```

## 场景缺口与重构

### 1. 同步编排 → 异步任务队列

**问题**：`run_chain()` 在 HTTP 请求线程中同步执行 6 个 Agent。
- 1 个 Agent 调用 LLM 耗时 3s，6 个串行 = 18s
- 10 个并发请求即耗尽 uvicorn worker
- HTTP 超时导致客户端 502，但 Agent 仍在后台运行

**重构方案**：
```
当前: POST /run → 同步执行 → 等待 → 返回结果
目标: POST /run → 返回 task_id (202) → 后台执行 → GET /status 轮询
```

### 2. Agent 并行化

C Agent（财务对账）和 D Agent（调度校验）无数据依赖，可并行执行。

并行后链路耗时：A(1s) + B(1s) + max(C(6s),D(4s)) + E(2s) + F(1s) = 11s（串行 15s）。

### 3. 状态机缺陷

**改进**：增加 FAILED 状态
- DRAFT → PROCESSING → PENDING_REVIEW → APPROVED|REJECTED
- PROCESSING → FAILED → PROCESSING (重试)

### 4. 配置缺失

已在 config.py 添加 `max_upload_size: int = 10 * 1024 * 1024`。

class TrackingService:
    """对接鲲鹏系统/城配平台获取实时物流数据"""

```

class AlertEngine:
    """基于规则的异常监测 + WebSocket 主动推送"""
    
    async def evaluate_and_push(self, ticket_id: str):
        rules = [
            ("delayed_delivery", "预计送达超时 30min+"),
            ("document_mismatch", "单据信息与系统不一致"),
            ("damage_reported", "签收破损"),
        ]
        for rule_name, desc in rules:
            if await self._match_rule(rule_name, ticket_id):
                await self._push_alert(ticket_id, rule_name, desc)
```
